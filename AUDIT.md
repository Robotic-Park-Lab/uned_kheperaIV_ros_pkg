## 0 — Blocking decision: `libkhepera-2.1` licensing

You asked to add `libkhepera-2.1` (used to build the C program that runs on the Khepera's onboard Linux, `scripts/server.c`) to the repo "si es lícito". Checked the actual library folder you left in this session's working directory: **no `LICENSE`/`COPYING` file anywhere in it**, and every source file header reads `Copyright (C) 2013 K-TEAM SA` with no redistribution grant of any kind — no SPDX tag, no "permission is hereby granted" clause, nothing. This repo (`uned_kheperaIV_ros_pkg`) is **public** and BSD-3-Clause licensed.

Vendoring proprietary K-Team source into a public BSD-3-Clause repo, with no license text granting that right, is not something I can call "lícito" from what's in the files themselves — it would read as Robotic Park Lab's own BSD-3-Clause code when it's actually all-rights-reserved third-party material. **Recommendation**: don't vendor the source. Instead, document `libkhepera-2.1` as an external prerequisite (same pattern already used for `cflib`/Bitcraze in the Crazyflie repo) — a short paragraph in the README pointing to where lab members obtain it (K-Team, or wherever you originally got your copy), plus a `Makefile` for `scripts/server.c` that expects it at a documented path/env var, without the vendor source itself living in this repo.

If you do have explicit permission to redistribute it (a K-Team agreement I have no way to see from the files), say so and I'll vendor it as you first asked — but I'm not doing that on my own judgment call given what's actually in the folder.

## 2 — Real bugs and dependency gaps

- [ ] **Real bug in the existing `experience.launch.py`** (`uned_kheperaiv_config/launch/experience.launch.py`, already present — this repo got ahead of the Crazyflie repo on the "one launch, one yaml per experience" idea): `for robot_id in physical_khepera_list:` iterates over `physical_khepera_list`, a **comma-joined string** (e.g. `"khepera01, khepera02"`), not a list — in Python this iterates **character by character**, spawning one broken `kheperaIV_client_driver` node per character instead of one per physical robot. Only correct today by accident when there's exactly 0 physical robots (the loop body never runs) or masked in testing. Real fix: split on `, ` into an actual list, or (better, matching how `uned_crazyflie_config`'s equivalent launch now works after that repo's restructuring) pass the joined string as a single node parameter instead of looping.
- [ ] **Undeclared dependencies**: `uned_kheperaiv_config`, `uned_kheperaiv_driver`, `uned_kheperaiv_gui`, `uned_kheperaiv_task` declare **zero** `<depend>` in their `package.xml` despite real imports (`rclpy`, `std_msgs`, `geometry_msgs`, `sensor_msgs`, `nav_msgs`, `visualization_msgs`, `tf2_ros`, `tf_transformations`, `PyQt5`, `rqt_gui_py`, `rqt_plot`, `yaml`, `numpy`...). `uned_kheperaiv_webots` declares 3 depends but is **missing `multi_agent_pkg`** (from `RoboticPark`), which `khepera_driver.py` imports directly (`from multi_agent_pkg.lagrange_multipliers import Sphere, Cone, Ellipsoid`) — identical gap to what was found and fixed in the Crazyflie repo for the same external package.
- [ ] **Lint tests failing**: verified with a real `colcon test` — **10 of 12 fail** across the 4 `ament_python` packages (same 10/12 ratio the Crazyflie repo had before its own cleanup). Mostly `E501` (line too long) and `F401` (unused import) in generated/compiled Qt code (`main_ui.py`, `logo_rc.py`) that should be excluded from lint like Crazyflie's was, plus real style issues in hand-written files worth fixing directly. One `test_copyright` also fails/skips for missing a copyright header in a generated file.
